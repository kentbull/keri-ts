# keri-ts

## 2.2.2

### Patch Changes

- 7ed9235: A receipt for a group this runtime is a member of, or for a controller with no end role to send to, is no longer attempted (and logged as "No end roles for ..." on every event); the responder decides there is nothing to send. `settleProposedRotation` takes a named `ProposedRotation` (route, event, smids, rmids) instead of a whole `GroupEventResult`. The live, ended and settled operation tables of the issuance and Unblind owners are private; read them through `liveOf`, `endedOf` and `settledOf`. `pendingApplies` and the wallet's `credentials.applies` can list answered Applies too (`includeAnswered`; each entry has a `state` and the `answer` that closed it), and `agreeFor` / `credentials.agreeFor` read the Agree that answers an Offer.
- 5480120: Constructing any `AppError`, `ValidationError` or other keri-ts error threw a `TypeError` in a browser bundle. `AppError` (and cesr-ts's `ParserError`) set their name from `new.target.name`, which the npm build rewrites into a call that needs `_dnt.polyfills.js`, and the browser entries never load it, so a routine error stopped the runtime that raised it. Every error class now names itself with a string literal, which also survives a minifier that mangles class names. The browser bundle gate now fails if anything a browser entry reaches contains the `import-meta-ponyfill` call.
- 77382e7: The elected member of a group forwards a completed group event to every other signing member when the Counselor completes it, so a member that never saw the signatures that completed it converges. `Counselor` takes a narrow `GroupForwarding` port (the runtime supplies `groupEventForwarding`, which replays the accepted event through the Poster); each member's outcome is a `GroupDelivery` and a failed member is retried with a doubling delay, never thrown (`forwardOutcomes` reads them). A member that only receives a group rotation (naming the members the group already has) or a reply that the proposer's signatures already complete now takes it on receipt without approving, as it does an interaction or a registry anchor.
- e0157cd: A group sends an Apply, Offer, Agree or Spurn through `proposeGroupNegotiation` (named `GroupNegotiationInput`), the same consent path as `proposeGroupPresentation` and `proposeGroupAdmit`; an exchange that requires anchoring is refused for a group. The wallet's group `credentials.present` now honours `verb` for all five and no longer substitutes a Grant for an Offer. `pendingApplies` lists the accepted, unanswered Applies addressed to a local identifier, and the wallet exposes it as `credentials.applies` beside `credentials.pinSchema`, which keeps schema bytes it was handed. The runtime already creates a group identifier's DH owner when its first message arrives, so no `ipex.dhke(group)` call is needed first; `group-admit.test.ts` no longer makes one. A group Grant that answers an Apply is pinned in `erpy` like any answer; the test covers it.
- fea14f3: A `/multisig` wrapper is checked before it is stored, noticed or listed: one addressed to an identifier the receiver does not hold, or sent by an identifier that is not a signing member of a group the receiver is in, is refused. A member that only receives takes a group interaction (or a registry proposal's anchor) that the proposer's signature already completes on receipt, without approving it; approving remains the way to add a signature. A proposal whose event is already accepted in the local KEL lists as `inapplicable` rather than `unapproved`. A receipt cue for the runtime's own group no longer tries to deliver to a group with no end roles. Rotations and replies still wait for approval; the lead does not yet forward a completed event to members that never saw its signatures.
- 04aa467: A host can supply held signers when it opens a Habery or a web wallet. `HaberyArgs.heldSigners` (type `HeldSigners`, a list of `Signer`s) is applied with `Manager.hold` as `openHabery` builds the Manager, before the Habery is returned, so the first mailbox poll of an identifier whose keys the host keeps (`makeSignedHab`) is signed; every opener built on `openHabery`, including `createHabery`, takes it, and `openWebWallet` forwards its own `heldSigners` option. Before, `openWebWallet` started its runtime before returning the wallet, leaving no moment for a host to hold a signer first. Held signers are still not stored: pass them at every open.
- b82217f: The IPEX disclosure API names the prior exchange by its SAID in `priorSaid` everywhere. `DisclosureBodyOptions` (and `GrantPreparationOptions`) close the option types of `prepareOffer`, `prepareGrantBody`, `prepareGrantFileBody`, `prepareGrant`, `PresentationOptions` and so `proposeGroupPresentation`: the builder's `prior` is no longer an option, so passing it is a type error and untyped input carrying it is refused with a `ValidationError` instead of being ignored (which sent an opening exchange). The `agree`/`spurn` presentation input renames `prior` to `priorSaid`. `storedExchangeWire` is exported from `keri-ts/runtime` as the exact presented bytes of a retained exchange.
- c887111: One Habery can now run both sides of one issuance Grant, as a host with two tenants needs: a member of the issuing group and a member of the receiving group, or an issuer and a holder. The issuance owner keys its live and ended operations by the Grant and the party (`partyKey`, `liveOf`, `endedOf`); `issuanceStatus`, `waitForIssuance` and `abandonIssuance` take an optional `IssuanceParty` (`{ role }`), and a Habery that holds both answers for the issuer and says so in the status `role`. A side of a Grant is finished (`partyComplete`) when its own exchange has retained its root, not when the shared Grant is accepted. An outbox message for a recipient held in the same Habery goes through the reactor in process, and a local group's members that are not held there are still delivered to. The DH and Unblind query receiver hands a query to every local party of the transaction, and a holder in the issuer's Habery finishes against the Grant the issuer already accepted. Unblind has the same one-operation-per-Grant keying and is not yet changed.
- 1cc1160: A non-transferable member of a group can now read its group's mailbox on a keri-ts mailbox host. Its poll carries a cigar (a non-indexed signature) and no source seal, and `authenticatesMailboxQuery` required a transferable requester, so every such poll answered 403 `Query requester is not authorized`. The host now verifies the cigar with the key in it and requires that key to be in the group's current key list: the key is the member's whole identifier, so the signature is the proof of control and the host needs no KEL for the member beyond the group's own. A signature by another key under the member's prefix, a key outside the list and a member whose key has left the list are still refused.
- bee9c32: Two fixes for a custodial host that keeps many identifiers in one Habery.

  A signer the host releases (`Manager.release()`) no longer ends a running runtime. The mailbox poll for an identifier whose key is not held, and any other background loop that needs one, hit `Missing prikey in db for pubkey=...` and the runtime task failed, as did restarting while the signer was released. The error is now a typed `SignerNotHeldError` (same message, with the public key). The mailbox poller ends such a poll as a new `unsignable` outcome and waits; every runtime loop (queries, Poster, cues, escrows, OOBI, authentication, signals, delegation, Counselor, KEL publisher, operation owners) restarts after one. Each waiting loop is listed in `runtime.signerConditions` (`SignerCondition`: loop, missing public key, since) and the wallet's `health()` reports `signer-unavailable` with that list. `Manager.hold()` now notifies `Manager.onHold` listeners, and the runtime uses it to resume the waiting loops at once.

  Several local identifiers may now advertise one ingress URL. A POST to the shared path used to answer 409 `Ambiguous hosted endpoint path` and a custodial host needed the `hostedPrefixes: []` policy to work. The handler now picks among the identifiers sharing the longest matching path by the request's `CESR-DESTINATION` (`resolveHostedEndpointPath` takes it as an optional argument); a request with no destination, or one naming none of them, still answers 409. Per-identifier paths are unchanged.

- 0aeed4e: A rotation's proposed new members can answer the proposal before they are signing members of the group. #996 made the multiplexor drop a wrapper from an identifier that is not a signing member of the receiver's local group; the approvals of a rotation come from the members it adds (for example the edge and service members of an enrollment), so the proposer never received them and the rotation never completed. A `/multisig/rot` wrapper from a non-member is now accepted only when it is named in the wrapper's own members and a stored wrapper for the same rotation from a current signing member or a local identifier names it too, so a sender cannot certify itself. A proposed member's approval that reaches another current member before the proposer's wrapper is dropped there; the completed event still reaches it by the lead's forwarding.
- 4d3ce74: A browser wallet under a strict Content-Security-Policy (`script-src 'self' 'wasm-unsafe-eval'`, no `'unsafe-eval'`) can now pin and validate schemas. Ajv compiled each schema with `new Function`, so `new Schemer` failed with "Invalid JSON Schema document." and Grant and Offer intake with it; the real `EvalError` was swallowed. Schema validation now interprets schemas with `@cfworker/json-schema` in every environment, with no code generation. It keeps what Ajv did here: `format` never rejects, schema documents are checked against their dialect's meta-schema (embedded as data), an invalid `pattern` fails when the schema is prepared, and the per-SAID prepared-validator cache is unchanged. The one new refusal is a schema using `$dynamicRef`, which the engine cannot interpret. "Invalid JSON Schema document." now carries the reason as its `cause`. cesr-ts takes cbor-x from its no-eval build, whose default build probes `new Function` at load, and the browser bundle gate now fails if any bundled code contains `new Function(` or a direct `eval(`.
- 9264cc1: A discloser's Unblind no longer drops a verifier's query as invalid when the issuer's KEL here has not reached the event anchoring a registry update: the query is held in `heldu`, the issuer's KEL is asked for through the ordinary query cue, and the query is answered when the event arrives (at the Grant deadline an unanswered one ends with a reason naming the missing anchor). A discloser whose presentation closed before it was asked ends its Unblind with the new non-failure state `unneeded` (`answerUnblind` returns at once with it). The refusal to Spurn a Grant that answers an Apply or Agree is kept, because KERIpy forbids it in both construction and verification, and now says what to do instead; the wallet library guide is corrected accordingly.

  The wallet's group `credentials.unblind` now reads and waits as the group's actual party (a discloser no longer reads as a requester), and a discloser with nothing begun reads `interrupted` instead of throwing, so its `answerUnblind` starts.

- 3223aed: One Habery can now hold both the discloser and the disclosee of a presentation and run both sides of its Unblind: live and settled operations are keyed by the Grant and the party (`unblindingKey`, `liveOf`, `settledOf`), `unblindingStatus`, `waitForUnblinding` and `abandonUnblinding` take an optional `UnblindingParty`, and a recipient held in the same Habery takes the bytes in process (new optional `reactor` dependency). The DH and Unblind query receiver hands a query between two local parties to both. `requestUnblind` after the verifier has answered the presentation throws the typed `PresentationClosedError` (an Admit or Spurn ends the discloser's authority; request the Unblind first). A refusal for an update that cannot be opened now says why (a random blinder cannot be derived from the registry root). A rotation proposal is taken on receipt only when it also names the group's current rotation members (`rmids`), not only its signing members.

## 2.2.1

### Patch Changes

- df59ad5: Group workflows that send a wrapper to every other signing member no longer fail on the first member that cannot be reached, after the event is already accepted locally. `publishProposal`, `approveGroupProposal`, `publishAcdcV2Registry`, `proposeRegistryEvent`, the legacy registry and credential proposals and the group endpoint role deliver to each member independently and report `members` (`GroupDelivery`: `delivered` with its destinations, or `failed` with the transport's reason) in their result, so the Counselor always starts and a caller can send a failed wrapper again; `Poster.canReach` still refuses an inception up front. The wallet's group event outcomes and `proposeMailbox` carry `members`, and Tufa prints them. Group issuance no longer sends its traffic to a member held in the same Habery.
- 22a06d8: A member that holds only the mailbox-delivered proposal of a fresh group DH issuance can now consent to it from the wallet. `groupIpexProposals` no longer lists a fresh issuance Grant (a Grant whose origin its own group issues, disclosed without registry proof), so `proposals.approve` takes the issuance call instead of the group IPEX one, and the two lists agree. `proposals.approve` returns `{ outcome: "refused", reason }` for an IPEX or issuance proposal the library will not approve yet, instead of throwing. A group member that approved a registry update now records the issued credential: `RegistryCustody.issuedOpening` derives the opening of the update that issued it. A non-elected member whose witness receipt fetch answers with a reply it cannot parse submits at its next attempt instead of after the 60 s grace. "ACDC v2 group graph is false or unresolved" now names each node's verdict and reason, and `authenticateIpexNode` rejections carry a reason.
- 9c8977a: A wait on an issuance, presentation or Unblind (`waitForIssuance`, `waitForPresentation`, `waitForUnblinding`) no longer settles while the live operation still holds a message in its delivery outbox: `IssuanceOperations.owes`, `PresentationOperations.owes` and `UnblindingOperations.owes` report it. A group issuer member's `tufa ipex grant --issue --resume` therefore stays until its DH contribution has been handed to the transport, instead of exiting at the `awaitingAnchor` phase with the contribution still queued (the KERIpy custodian then never reached DH quorum and its operation expired). `tufa multisig join --kind <kind>` approves only a pending proposal of that kind (and refuses a `--said` of another kind), so a join never signs an unrelated pending proposal; without `--kind` it still approves the first pending one.
- 02912da: `tufa ipex` group commands with `--acdc-v2` publish the group proposal before the approval wait, so `--approval-timeout 0` still proposes and the pending result lists the published member wrappers (`messages`); `groupIpexMessages` reads them from a live or ended group IPEX operation. Two stale `tufa` CLI test expectations are updated (`--timeout` on `delegate confirm`; the admit command's refusal of a Grant that intake never accepted).
- efc0015: `tufa multisig rotate` and `tufa multisig join` report the registry root copies an accepted group rotation caused whichever of the command and the runtime's owner loop sent them first: copies the loop sent after the rotation cue prompted the replicator, before the command's own pass, are read from the sent marker and printed as transmitted `root_copy` lines.

## 2.2.0

### Minor Changes

- 2e21439: Add `approveGroupProposal` to `keri-ts/runtime` for key-event (`icp`, `rot`, `ixn`) and endpoint-role reply (`rpy`) group proposals. It acts only on the wrapper SAID it is given and never prompts: it signs this member's contribution, sends it, hands the group event to the Counselor and returns the `GroupEventRef` without waiting for other members. A repeated call after a crash reuses the member's recorded signatures (read from `sigs.`) and its stored wrapper instead of signing or prompting again. `approvePendingMultisigProposal` and `MultisigApprovalCallbacks` are unchanged.
- c550909: Add a polyfill-free `browser` export condition to the browser-safe entrypoints (`cesr-ts`, and `keri-ts`, `keri-ts/runtime`, `keri-ts/db`, `keri-ts/db/indexeddb`) so bundlers no longer pull `node:module`, `node:url` and `node:path` through DNT's polyfill import. `import` and `types` targets are unchanged; the Node-only subpaths get no `browser` condition.
- f83f935: `tufa delegate confirm` waits for the one thing it needs instead of a fixed 15 s window. `waitForPendingDelegation` observes the delegator's own `delegables.` escrow and `waitForDelegationAnchor` observes a group delegator's anchor until it is receipted; both live in `keri-ts/runtime`, take a caller-supplied `timeoutMs` and return a typed `settled` or `timed-out` outcome. The command gains `--timeout <seconds>` (default 30) for both waits, and its timeout errors now say which request or anchor never arrived. A test drives a group delegator's confirm path through these calls with a second member approving the proposal through `approveGroupProposal`.
- 2988f94: Add `listPendingDelegations`, `approveDelegation`, `delegationApprovalStatus`, `settleDelegationApproval`, `waitForDelegationApproval` and `dismissDelegation` to `keri-ts/runtime`. They own a single-signature delegator's approval of a delegate's pending `dip` or `drt`: discovery from the `delegables.` escrow, the anchoring event, witness receipts, the witness-log request for the delegate and the wait for the delegate's event. A repeated approval finds the anchor in the delegator's KEL and never anchors twice. `tufa delegate confirm` now calls them with unchanged behavior for single-signature delegators; the group path is unchanged.
- aaa2ff2: The runtime's operation owners keep an in-memory table of live operations only; their status is derived from the protocol stores. `IssuanceOperationStore`, `PresentationOperationStore`, `UnblindingOperationStore`, their `Memory...` implementations, the `IssuanceRecord`, `PresentationRecord` and `UnblindingRecord` types, the `store` dependency of every owner and the `operationStores.issuance`, `.presentation` and `.unblinding` options are removed with no replacement; backward compatibility with 2.1.0 is not kept. `issuanceStatus`, `presentationStatus` and `unblindingStatus` read the pending Grant and its deadline, the held registry root, the registry head, the accepted exchange, the accepted Admit and the peer's stored answer, so a reopened store reads what it read before, except for what lives only in memory: the transient phases, the `abandoned` and `failed` reasons, consent times and the destinations of a delivery. An issuer that ended between staging and anchoring reads `interrupted`; an explicit recovery action is planned for a later release. `resendPresentation(ops, said)` delivers a signed presentation again after a restart by rebuilding its wire from the stored signatures, without signing. The one remaining embedder port is `operationStores.derived`; it now defaults to `BaserDerivedUpdateStore`, which keeps the blind-derivation coordinates durably in the registry database (`dvus.`, a keri-ts-only sub-database). Wire formats are unchanged.
- b1c58c2: Recover DH issuance after a process restart from stores alone. `Dhke.approve` now lets a new exchange from a registry's issuer overwrite a held root that was never used: the registry has no update accepted or escrowed. The old root is overwritten only when the new exchange retains its own, so an interruption before that leaves the old root; once an update is staged or accepted the refusal is unchanged. `Manager.putRegistryRoot` takes an optional `overwrite` flag for this and `Manager.hasRegistryRoot` reads root presence without decryption. A process now refuses a second live DH operation on the same registry. The runtime issuance owner settles records an earlier process left active on its first `processOnce`: an issuance that had not anchored reads `interrupted` and needs a new Grant, a holder that kept its root waits and completes by itself when the update is accepted (`Dhke.resume`, `Dhke.finish` proves the held root against the update, a wrong root is refused with a reason and the Grant stays unaccepted), and an issuer that anchored but did not finish completes without signing or anchoring again. Nothing is signed after a restart. A Grant past its deadline reads `expired`, with a reason that asks for a new Grant when the update had already arrived. A KERIpy peer keeps the old rule and refuses a second exchange on a registry it holds a root for, so with a KERIpy holder the issuer needs a fresh registry.
- 49f9be9: Add `receiptEvent`, `beginDelegation`, `delegationStatus`, `waitForDelegation` and `completeEvent` to `keri-ts/runtime`. They own the steps after authoring a single-signature event, witness receipting and delegation begin-and-wait, so library hosts such as a browser wallet need not reimplement what `tufa incept`, `rotate`, `interact` and `witness submit` do. The CLI commands now call them with unchanged behavior.
- 1e33f52: Add `Counselor` to `keri-ts/runtime`: group-event completion on KERIpy's `gpse`, `gpwe` and `cgms` rows for the signature and witness stages. It tracks an event across restarts, never signs, removes an escrow row by exact event instead of by prefix, judges witness receipts against the event's own witness set, and lets a non-elected member submit receipts after a configurable grace so an offline elected member cannot stall the group. Also adds `groupWitnesser` (KERIpy `_groupWitnesser`), `waitForGroupEvent`, and a `"group"` workflow change kind. Nothing calls the Counselor yet.
- 62f339e: Add the delegation stage to `Counselor` in `keri-ts/runtime`. A delegated group inception or rotation waits for its delegator: the publishing member (elected, or any member after `fallbackAfterMs`) begins the existing Anchorer and the Counselor records completion; other members query the delegator's witness, pin the anchor seal and finish through witness receipts. Adds `supply`, a `proxy` input, the `proxy` and `delegatorUnknown` block kinds and the optional `GroupDelegation` constructor collaborator. `status` now reads `pending` for a counseled event whose body is not stored yet, `start` no longer retains inputs for a complete or superseded event, and `abandon` publishes one `<pre>:<sn>` change per removed event. The delegator-anchor query with backoff is now a shared function used by both the Anchorer and the Counselor, with unchanged Anchorer behaviour.
- 608f815: Add `runtime.counselor` to `AgentRuntime` and run its loop in `runAgentRuntime`, beside the delegating loop; the runtime pending state gains `groupPending`. The Counselor acts only on events registered with `start` or `supply`, so a runtime with nothing counseled does no extra work beyond three row counts per turn. A delegated group event now proceeds with the local group member hab when no proxy is supplied, as in KERIpy, so the `proxy` block kind is removed; an explicit proxy still wins.
- 7c0a7f2: A group delegator approves a delegated event through the group proposal API. `proposeGroupDelegationApproval` (exported from `keri-ts/runtime`) proposes the group interaction that seals the delegated event, hands it to the Counselor and publishes it to the other members, who approve it with `approveGroupProposal`; it returns null once the group's KEL already holds the anchor. `requestDelegatedEvent` then asks the delegate's witness for the delegated event, and `delegationApprovalStatus` / `listPendingDelegations` already work for a group delegator. `tufa delegate confirm --interact` on a group calls these instead of its own `interactGroupHab` flow and hand-built `/multisig/ixn` message; the printed lines are unchanged, and the second run now waits for the anchor's witness receipts before asking for the delegate's event. The CLI-held group branch is removed rather than wrapped; backward compatibility with 2.1.0 is not a goal for 2.2.0.
- 6705181: Group DH issuance runs in the runtime. A local group issues or receives a v2 DH credential through `runtime.operations.issuance`, the same live table, `issuanceStatus` and `waitForIssuance` as an individual, so a browser wallet with no CLI can act as the custodian or as a non-custodian member. New explicit calls (each may sign, none waits on a remote): `prepareGroupIssuance` (the custodian's first partial Grant and the proposal), `beginGroupIssuance` (an issuer member's Grant contribution and consent to its DH query contribution; the custodian may pass a credential instead of a proposal), `approveGroupIssuanceExchange` (a holder group member's consent) and `followGroupIssuanceProof` (verifies the custodian's final proof without signing). `groupIssuanceProposals(ops, group)` lists the stored Grant proposals a member may consent to and `groupIssuanceProof` exports the custodian's public proof. The owner's `processOnce` now performs the group steps: it sends each member's own proposal, authenticates the Grant, approves DH, sends the custodian's evidence, query and reply traffic, takes wrappers in, finishes the Grant, proposes the registry update through `proposeRegistryEvent` and broadcasts the proof to the other members. Root copies are sent once per member by the runtime's `RootReplicator`. A member that reloads reads `awaitingExchangeConsent` for a pending Grant and consents again with the same call; a custodian that reloaded after retaining its root reads `interrupted`, since the frozen coordinator and custodian are not stored. `IssuanceDeps` gains an optional `group` (the multiplexor and the registry proposal collaborators; the runtime composes it), `IssuanceDelivery.deliver` takes an optional `topic`, and `IssuancePhase` gains `awaitingGrantSignatures`.

  `@keri-ts/tufa`: `tufa ipex --issue` and `tufa ipex setup` for a group are callers of these calls and keep their flags and output. The orchestration in `ipex-group-issuance.ts` is removed with no replacement: `acceptGroupIssuanceProof` and `awaitGroupIssuanceProof` become `acceptGroupDerivedProof`, `prepareGroupDerivedIssuance` no longer takes a wallet, and `--witness-gvrsn` no longer reaches the group path.

- 9bc1f81: Closes the last CLI-only group behaviour and the gaps left by the group issuance work.

  - A group custodian is told from a member that was sent a root copy by what the stores hold: `deriveGroupCustody(deps, hab, grant)` now takes the Grant and returns null when a `/registry/root` copy was sent to the local member for a disclosed registry, so a member holding a copy of a still-pending Grant is never adopted as the custodian.
  - The issuance owner scans for resumable Grants every `ISSUANCE_SWEEP_MS` (5 s) instead of once, so a custodian that reloaded while its registry update awaited the other members resumes when the update is accepted.
  - Delivery goes through one outbox with retry for every owner (`DeliveryOutbox`). Presentation and Unblind deliveries, single and group, keep the signed bytes on a failure and retry them with a doubling delay until the Grant's deadline, like issuance. `PresentOptions`, the `maxAttempts` option of `present`, `PRESENTATION_RETRY_MS` and `PRESENTATION_MAX_ATTEMPTS` are removed; an exchange with no deadline ends `failed` after `PRESENTATION_RETRY_BOUND_MS` (10 minutes) of failures. The wallet's `present` and `requestProof` lose `maxAttempts` too.
  - A group presents with a presentation registry through the library: `proposeGroupPresentation` accepts `presentationRegistry`, proposes the registry update, and the group IPEX owner signs the member's contribution to the Grant once the group has accepted the update (`proposeGroupIpexAfter`, `GroupIpexPrerequisite`, phase `awaitingRegistryUpdate`). The other members approve the update with `approveGroupProposal` and the Grant with `approveGroupIpex`.
  - The exact-file group presentation moves into the runtime: `preparePresentationFile`, `resumePresentationFile` and `deliverPreparedGrant` hold every check of what a file may change, and the elected lead's delivery is a presentation operation with the same retry. `tufa ipex` for these files only reads and writes them; `preparePresentationGrant` and `resumePresentationGrant` are removed with no replacement.

- 812940d: A group holder admits through the library. `runtime.operations.groupIpex` (`GroupIpexOperations`) owns a local group's v2 IPEX messages: `proposeGroupAdmit` (or `proposeGroupIpex` for any group-authored message, with its nested evidence) and `approveGroupIpex` are the explicit member consents; `groupIpexProposals` lists the stored proposals a member may approve; `groupIpexStatus` is a pure read derived from the stores and `waitForGroupIpex` only observes. The owner loop publishes each member's wrapper, retries a member that is briefly offline with a doubling delay (`RetryBackoff`), collects the other members' stored contributions, authorizes graph use and lets the elected lead send the completed message. `approveMultisigIpexLocally` splits a member's local approval from publication and delivery, and `findStoredMultisigIpex` and `groupIpexApproved` read the stored proposal. `tufa ipex admit --acdc-v2`, group `ipex grant` and `tufa ipex join` for ACDC v2 group messages are callers of these calls and keep their flags and output.
- 1f09ff2: Group DH issuance takes plain signatures and derives what it can. The group is derived from the Grant, the proposal or the credential's registry instead of being passed as a selection: `prepareGroupIssuance(ops, draft, coordinator?)`, the new `proposeGroupIssuance(ops, draft, options?)` (prepare, then the custodian's own approval in one consent), `approveGroupIssuance(ops, grant, options?)` (an issuer member's consent, replacing `beginGroupIssuance`), `approveGroupIssuanceExchange(ops, grant, coordinator?)`, `followGroupIssuanceProof(ops, grant, options?)` and `groupIssuanceProof(ops, grant)`. `groupIssuanceElection(ops, group, coordinator?)` is a pure read of the custodian a coordinator elects and whether the local member is it. The coordinator is an optional pin that defaults to the group's latest establishment event, and the custodian is always the election's: `--custodian` on `tufa ipex` is optional and only asserts it, and `--coordinator` is optional. `approveGroupIssuance` also refuses a proposal the elected custodian did not sign, so an election disagreement fails at consent instead of stalling DH. `GroupIssuanceSelection`, `BeginGroupIssuanceInput`, `beginGroupIssuance` and `GroupBegin` are removed with no replacement; `GroupIssuance` is built from a `GroupParty`, and `deriveGroupCustody` returns a `GroupElection`. The wallet's group `issue`, `proposals.approve`, `receive` and `unblind` call the new functions. keri-ts `AGENTS.md` gains the plain-signature and composition rules.
- dd432c5: `tufa multisig join` selects and approves stored proposals through the library: it lists them with `listGroupProposals` (or finds the `--said` one with `findGroupProposal`), asks the user for each unapproved proposal in notice order, approves only one that gets a yes with `approveGroupProposal`, and then waits on the runtime Counselor for receipts and delegation. `--auto` still approves the first pending proposal without asking, as KERIpy's `kli multisig join --auto`, but only inside the `join` command; no other command signs a proposal it was not asked to sign. A declined proposal is asked about once per command. `join --group <alias>` with nothing to join resumes the group's own latest event through the Counselor. The CLI-held `receiptAcceptedEvent`, `completeDelegationIfNeeded`, `waitForGroupAcceptance` and the stored-proposal polling loops are removed; backward compatibility with 2.1.0 is not a goal for 2.2.0.

- b7e436e: The issuance owner now resends its DH query freshly signed each second instead of repeating the same bytes until the sender's own KRAM window had passed. ### Minor Changes

- Release 2.1.0 for every published package. It adds the SEDI `I1I` and `DI1I` issuer-identity Edge operators with KERIpy's open Grant walk as the default, a pluggable store contract (ADR-0015) that lets `keri-ts/db` and `keri-ts/runtime` be bundled for a browser over `MemStore` or IndexedDB-backed `WebDBer`, automatic registry root replication to group members at issuance and after rotation, and KERIpy's handling of v2 ACDC sections without a top-level `d`.

  **Breaking changes**

  - The native LMDB surface moves from `keri-ts/db` to `keri-ts/db/lmdb`: `LMDBer`, `PathManager`, `openLMDB`, the `create*` store factories and, from `keri-ts/runtime`, `createHabery`. `openRegistry` requires an `opener` and loses `web`; `openLmdbRegistry` is the LMDB default.

  - `Baser`, `Keeper`, `Reger`, `Noter`, `Mailboxer`, `RegBaser`, `WalletBaser` and `VerifierCueBaser` compose over an injected `DBer`; their constructors take a store and their LMDB path statics become `Family`. `Suber`, `Komer` and `LMDBer` table methods take an opaque `Table`.
  - `LMDBer` behavior: empty dupsort values and empty or over-long keys throw `DatabaseKeyError`, `addVal` no longer accepts `null`, duplicate reads of an empty key report absent, and failures raise `DatabaseKeyError`, `DatabaseNotOpenError` or `DatabaseOperationError` instead of a bare `Error`.
  - Config files move from `keri/cf/{base}/{name}/{name}.json` to `keri/cf/{base}/{name}.json`, the default `Configer` base is `main`, and the `--compat` home fallback is `~/.keri/cf`. Absolute `--base` and names are refused, the store directory is set to owner-only mode on every open, and an unusable store directory falls back to the home directory.
  - Delivery to a recipient, witness or mailbox whose latest accepted event is KERI v1 fails with `PeerVersionError` instead of sending v2.
  - Grants walk open by default, as in KERIpy. `walkIpexGraph` takes a `"open" | "closed"` policy instead of a boolean and `AcdcGraph` carries it as `walk`; pass `grantWalk: "closed"` for the 2.0 refusal of every Grant that omits a far node.
  - Edge chain evaluation follows KERIpy more strictly: unrecognized unary operators and `NOT` are non-retryable unknowns, every schema pin is checked, and a list, falsy or `n`/`w`-bearing Edge Section is malformed.
  - A v2 ACDC attribute, edge or rule section without a top-level `d` is no longer given one. The bytes and SAID built for such a body change to KERIpy's; credentials authored by 2.0.x keep their inserted `d` and still verify.

- f05aff1: Breaking: add a Grant walk policy, `grantWalk: "open" | "closed"`, to `loadIpexHandlers` and `AgentRuntimeOptions`. The default is `"open"`, matching KERIpy. Under `"open"` a far node the Grant does not carry is a permanent unknown: an OR group with a valid sibling accepts, and an AND group or a sole Edge refuses at once without escrow. `"closed"` refuses any Grant that omits a far node, as every Grant did before. A node the disclosure plan selects but the Grant does not nest refuses under both. The internal `walkAcdcGraph` and the exported `walkIpexGraph` now take the policy instead of a `closed` boolean, the exported `AcdcGraph` interface requires it as `walk`, carrying it into `evaluateChain`, and `ipexGrantWalk(exchanger)` returns the configured policy. - c0b4f45: Breaking: delivery now fails with a typed `PeerVersionError` instead of sending KERI v2 to a recipient, endpoint or mailbox provider whose own latest accepted event is v1. A deliberate `--version 2.0` rotation can now upgrade a v1 identifier.
- bef3fd9: Add the SEDI issuer-identity Edge operators `I1I` (near and far ACDCs share an issuer) and `DI1I` (the near issuer is the far issuer or an anchored delegated descendant of it), following KERIpy PR 1757. Missing delegation evidence escrows as retryable; a wrong ancestry or DND refuses.

- 89303e5: Breaking: add the backend-neutral `DBer` store contract and opaque `Table` handle from ADR-0015. `Suber`, `Komer` and their families now take a `DBer` and hold a `Table`, and `LMDBer`'s table methods take a `Table`, so `sdb` is no longer typed as an lmdb-js database; LMDB-specific code reaches the native handle through `lmdbTable()`. ## 1.0.0

### Breaking API and architecture changes

- Restrict supported package entrypoints to explicit root/runtime/db and CLI
  helper surfaces; remove implementation deep-import patterns and unused exports.
- Use concrete KERIpy-shaped owners, data cues and Decks. Query records carry
  their required q body. Reactor handles protocol intake/escrows rather than
  arbitrary application callbacks; transport does not discover AgentRuntime.
- CLI and hosts share workers with elapsed completion and joined cancellation.
  Remove serial runtime pumps, finite mailbox turns, application budgets, outboxes
  and unsupported mailbox/KRAM business acknowledgements. Preserve protocol
  escrows, replay/timeliness caches, mailbox messages/cursors and real cleanup.

### Protocol and interoperability

- Support complete IPEX apply/offer-through-admit and legal spurn workflows,
  independently authenticated credential chains, nested edge operators and
  progressive multi-attribute disclosure without changing commitments or expanding
  earlier stored partial evidence.
- Support TS DI2I approved delegation chains and NOT over authenticated node
  validity and receiver-accepted issued/revoked facts. Missing, malformed, forged
  or unknown evidence cannot satisfy negation. These operators remain excluded
  from Python interop while the reference does not implement them.
- Correct v2 mailbox forwarding to carry a signed child-body digest and qualified
  nested evidence. Keep KRAM authentication distinct from downstream acceptance;
  preserve threshold-completion receipt time across dependency retry and replay.
- Derive historical witness cohorts/thresholds from accepted event ancestry.
  Keep node issuer/registry authentication independent of conversation policy,
  and publish registry state atomically through its concrete owner.
- Project DID documents from accepted state; keep actual OOBI convergence,
  complete artifact intake, transport-fallback rules and joined cleanup explicit.

### Packaging

- Preserve valid strict NodeNext declarations for LMDB 3.5.3 and the actual
  public manager, storage, host and ingress contracts.
- Installed-package qualification exercises native large-row read/reopen,
  cryptographic signing/refusal, TCP transmission/close and CLI/HTTP operation
  before installing compiler tools. The supported Node floor remains 20.3.
