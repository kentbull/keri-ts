# 2.2.6 release notes

Published versions: to be filled in at release.

2.2.6 fixes the costs that made a long-running issuer slow and made group issuance fail. Nothing here
changes a wire format, an event or the signature of a call. The notes are grouped by fix. PR numbers
are in parentheses. Package changelogs list every change.

## Why this release

A consumer ran a long-lived issuer and saw it slow down as its event log grew. It uses one registry
per credential, and each issuance adds about two events to the issuer's log, so the log grows with
every credential. Group issuance also failed near 58 credentials. The causes were not in one place:
some resent work that did not need resending, and some sent a whole log where a delta was enough.

## Fixed

### A group's threshold query was resent without bound (#1092)

A group's DH or Unblind query cannot be re-dated by one member, because every member must sign the
same bytes. The sender could not make a fresh query, so it resent the unchanged one every second
with no limit.

- **Sender.** A group sender now backs off from 1 s to 8 s between resends. It stops resending once
  the query is older than the multi-key KRAM acceptance window, since the receiver would refuse it
  by then. The operation still waits until its own deadline.
- **Receiver.** A byte-identical copy of a query the receiver already accepted is a duplicate: the
  receiver does not verify it again, does not add a new signing contribution, and re-sends the stored
  reply at most once a second.
- **Single-signer paths** still re-date each resend. They are unchanged.

### Proof support was sent whole twice per issuance (#1090, #1094)

Issuance sends the Grant with its proof support, waits for the holder's query, proves, and sends the
support again. The second send repeated everything. It now carries only what proving added: the
anchoring event and the registry update. This holds for single-signer issuance (#1090) and group
issuance (#1094). An operation rebuilt after a restart no longer knows what it already sent, so it
sends in full.

### A relay-mode sender introduced its whole log on every send (#1090)

A sender in relay mode re-introduced its whole event log to its relay on every send, because the
relay never receipts each new interaction event, so the sender never saw its log as delivered. It now
introduces only when its record (`kpub`) shows the relay lacks its current establishment event.

### A registry event without its anchor now asks for the issuer's log (#1089, #1093)

A registry event is held until the issuer event that anchors it arrives. Before this fix the
recipient waited without asking. It now sends the issuer a `logs` query once, from the first event of
the issuer's log that it lacks. This covers the v1 registry processor (#1089) and the v2 registry
path (#1093). Retries of the held event do not ask again.

## Interop

The KERIpy candidate is `kentbull/keripy` `v2-spec` at `06aa382e`. It adds the same missing-anchor
query on its v2 path (kentbull/keripy#191).

## Not tested

- A browser edge with IndexedDB under a long issuer log.
- Group Unblind requester resend under a fake clock.
- The relay path of the missing-anchor query, end to end.

## Known limits

- A relay that lost its store drops forwarded messages silently until the sender's next mailbox poll
  is refused and the sender republishes its log. There is no typed refusal for a forward from an
  unknown sender yet.
- The sender judges the query acceptance window from its own KRAM settings. A store that never ran
  KRAM has no window, and a group sender there resends every 8 s until the deadline.
- v2 registry events do not carry the anchor's sequence number. The query's upper bound comes from the
  sender's hint when there is one.
- Grant authentication does not yet raise the query. A Grant that arrives before its registry
  inception is accepted is refused, not held, so the sender must send it again.
- A group member that alone meets the threshold still cannot re-date a group query.
- Each Grant still carries the issuer's whole log on its first send. Sending only what a contact
  lacks, and bounding a new contact's cost, are planned work.

## Upgrade

There are no API or wire changes. This is a patch release; upgrade in place.
