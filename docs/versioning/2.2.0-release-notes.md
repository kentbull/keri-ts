# 2.2.0 release notes

Published versions: **cesr-ts, keri-ts, @keri-ts/hosting and @keri-ts/wallet
2.2.0**. @keri-ts/registrar, @keri-ts/verifier and @keri-ts/observer are
unchanged at 2.1.0.

@keri-ts/tufa was tagged `tufa-v2.2.0` but **not published** at 2.2.0. Its
release workflow runs the package's own tests before publishing, and two
expectations in `packages/tufa/test/cli.test.ts` were stale, so the workflow
failed before any publish step. The tag stays on the remote, unpublished and
unmoved. The expectations were fixed on master afterwards (#987), and Tufa ships
in 2.2.1. Until then the latest Tufa on npm is 2.1.0.

2.2.0 is a minor release on the 2.x line: it adds behavior to the library and
wallet surfaces. For caller actions and the surfaces that moved, read the
[migration guide](../reference/compatibility/MIGRATING_FROM_2_1.md). For how a
host composes the wallet and runtime, read the
[wallet library guide](../design-docs/runtime/WALLET_LIBRARY_GUIDE.md). Package
changelogs list every change.

## Included behavior

- **Browser store and wallet.** `keri-ts/db/indexeddb` persists `WebDBer` stores
  to IndexedDB, single-writer by default through a Web Locks lock. The browser-safe
  entrypoints gain a polyfill-free `browser` export condition. `@keri-ts/wallet`
  gains the browser-safe `@keri-ts/wallet/web` entry and `openWebWallet`, the
  browser composition root, with a wallet-level API for identifiers, OOBIs,
  groups, proposals, credentials and presentation. The LMDB-backed
  `createWalletBaser` moves to the Node-only `@keri-ts/wallet/lmdb`.
- **Library-first workflows.** `keri-ts/runtime` owns steps that only the CLI
  carried: event receipting and completion, delegation begin, wait and approval,
  the single-signature IPEX conversation, holder receive and poll-and-settle,
  and OOBI waits. Tufa commands call these; library hosts such as a browser
  wallet need not reimplement them.
- **Counselor and group proposals.** `Counselor` completes group events across
  restarts. The group proposal API (`proposeGroup...`, `approveGroupProposal`,
  `listGroupProposals`) covers inception, rotation, interaction, endpoint-role
  replies, delegation approval, registries and mailbox authorization.
- **Runtime-owned issuance, admit, presentation and Unblind.** Issuance, Admit,
  presentation and Unblind run in the runtime for single identifiers and local
  groups, with one delivery outbox that retries until the Grant's deadline. DH
  issuance recovers after a restart from stores alone, and pending DH and Unblind
  requests persist across restarts.
- **KelPublisher and mailbox poller.** Telling mailboxes about a rotation moves
  onto the `KelPublisher` runtime reaction. A group's KEL submission carries the
  signing member's KEL so a mailbox host can authenticate that member's polls.
- **Custody hooks.** `Manager.hold` and `Manager.release` borrow live signers
  without any Keeper table receiving the key, and `Habery.makeSignedHab` adopts
  an inception the caller built and signed.
- **Fixed-tock runtime loops.** Escrow processing, the operation owners, the KEL
  publisher and the remaining background loops of `runAgentRuntime` run as
  fixed-tock doers on the runtime clock instead of zero-delay loops.
- **Hosting.** The CORS preflight allows the `CESR-Genus` and `Authorization`
  headers, and OOBI and DID resolution wait on the OOBI they were asked for.

Known limits are recorded in the migration guide and the wallet library guide
above and in the [parity roadmap](../plans/PARITY_ROADMAP.md).

## Known defects in 2.2.0

Found by qualification so far; they are fixed in 2.2.1 or later.

- A command or caller that returns when an operation reaches a phase can exit
  before that step's queued delivery is sent. This was seen as a mixed group with
  a KERIpy custodian expiring.
- In a browser wallet, a group member's consent to a group DH issuance through
  `proposals.approve` fails.
- Group inception and group registry steps wait about 60 s in the browser group
  lane.

## Qualification

2.2.0 was published at commit `f1b0e618d5d1dd02f57fc0b4b3447acfe0535799`
before the full qualification battery completed. Qualification is in progress,
and any regression it finds ships as 2.2.1.

What had been run: narrow unit tests with each PR; and one full CI run plus a
local interoperability pass at PR #937, before the last roughly 47 PRs merged.
The release commit passed the static, manifest and version checks. The package
workflows ran each published package's own tests, builds and smoke checks. The
full source, interoperability, manual and installed-artifact battery was not run
at the release commit.
