# 2.2.3 release notes

Published versions: **keri-ts and @keri-ts/wallet 2.2.3**. The tags `v2.2.3`, `keri-v2.2.3` and
`wallet-v2.2.3` are at `cc2fbaf9`. The packages were built by a workflow dispatch on master one
workflow-only commit later; the package content is identical. Other packages stay at the versions
in the [2.2.2 notes](2.2.2-release-notes.md).

2.2.3 adds one library behavior, replacing a group habitat's local member after a rotation, and
fixes two races in the interop test fixtures. Nothing here changes a wire format or an event.
Package changelogs list every change.

## Replacing a group's local member (#1024)

A local group habitat records one local member: the habitat in the Habery that signs, polls and
contributes for the group. Membership changes only by a rotation, and the record did not follow
one. After a rotation that removed the recorded member, the record named a habitat that could no
longer sign, and `Habery.joinGroupHab` refused any different member.

- **The rule.** `joinGroupHab` now replaces the recorded member only when the group has accepted
  key state, the recorded member is in neither the signing nor the rotation members of that state,
  and the new member is in one of them. It refuses otherwise, including while the group has no
  accepted state, because the recorded member cannot be judged then. The decision reads the accepted
  Kever and the members' KELs, never the caller's lists or a proposal. A Habery that holds two valid
  members of a group therefore never switches silently.
- **No event, no signature.** The call changes local record state only.
- **The record.** The replacement keeps the record's name, domain, `sid` and `watchers` (the old
  write dropped the last two, on any rejoin), and the stored member lists are brought in line with
  accepted state.
- **`replaceGroupMember(runtime, { group, member, smids, rmids? })`**, exported from
  `keri-ts/runtime`, and the wallet's **`groups.replaceMember(group, { member, smids, rmids? })`**
  call `joinGroupHab` and then end the work bound to the old member. Use them rather than
  `joinGroupHab` alone when a runtime is running.
- **What is cleaned up.** Escrowed registry root copies addressed to the old member, and the markers
  of copies sent to it, are removed. Live issuance operations whose party member or frozen DH
  custodian is the old member, and live Unblind operations that hold it, end as `abandoned` with the
  reason "Local member X of group G was replaced by Y"; ending them releases their held `heldq` and
  `heldu` rows.
- **What stays.** Rows keyed by the group stay: registry roots (`rroots`), mailbox cursors, held
  queries of other operations and the credentials the group holds. The new member needs no root copy
  from a peer when the Habery already holds the group's roots. The publisher re-posts the new member's
  KEL to the mailboxes.
- **What is left running.** Group IPEX messages and presentations keep no member binding (their
  contributions are already signed and the member is read live), so they run on. An exchange the old
  member led is not resumed. Ended operations are not carried over: start a new proposal.
- **The wallet's approval workflow** joins a group only the first time. Replacing the member is this
  explicit call.
- **Behavior change.** Delegation's second `localGroupMember`, which returned null, is gone. For a
  local group whose recorded member habitat is missing, the delegation workflow now throws instead of
  falling back to the communication habitat.

### Not tested

- A real issuance or Unblind carried through a replacement. The tests end stand-in live operations on
  the real owner classes, and check the held-row release against stand-ins.
- Presenting a credential the group was granted before the member changed, including DH and Unblind
  for it. This was read from source (credentials, roots and party keys are keyed by the group) and not
  run.
- A success case through the wallet. One wallet cannot drop its own recorded member by a rotation it
  proposes, so the wallet test covers the wiring and the refusals only.

## Test fixtures (maintainer-only)

- **#1027.** The KERIpy IPEX peer fixture answered an empty `200` when a command had no result, and the
  interop test client parsed every answer as JSON. A poll that ran before the issuer had staged a
  group event failed with `Unexpected end of JSON input` instead of polling again. This failed
  `interop (interop-ipex-disclosure)` on dispatched stage-gate runs. The fixture now answers `null`.
- **#1028.** The same pattern in the legacy group peer fixture, and a shared parser for the five other
  fixture clients that rejects an empty answer and names the action.

## Release tooling (maintainer-only)

These change no published package.

- **#1020.** The release check is skipped when a recorded green `PR Stage Gate` run covers the exact
  tree being released, and otherwise runs as shards. A `pull_request` run never counts, because it
  tests a synthetic merge commit.
- **#1022.** A `Release train` workflow publishes the packages in dependency order and qualifies each
  distinct commit once.
- **#1025.** The release tooling runs from the workflow's commit, not the tag, so old tags can be
  released with the current checks. A tag whose content lacks what the current shards call runs the
  serial historical commands instead.
- **#1029.** Publishing now runs after a skipped release check. The skip was applied to `publish` and
  `github-release` through an implicit success condition.
- **#1030.** The train no longer calls the shared release workflow to publish. npm trusted publishing
  validates the calling workflow's name, so a publish from a reusable workflow was refused with a 404.
  The train now dispatches each package's own workflow, which can also release one package from an
  existing tag.
