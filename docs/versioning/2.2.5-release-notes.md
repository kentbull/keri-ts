# 2.2.5 release notes

Published versions: **TO BE FILLED IN by the version PR.** The package set, the tags and the release
commit are decided there, not here.

2.2.5 closes a group of ways a remote party could end an agent's runtime, adds relay mode (an edge
that delivers through its agent), finishes group member replacement and wallet recovery, and makes
KRAM refusals visible. It also replaces callbacks and registries inside the runtime with cues, decks
and state reads. Nothing here changes a wire format or the bytes of an event. Several exported names
are removed or changed; the [Breaking changes](#breaking-changes) list gathers them. Package
changelogs list every change.

The notes are grouped by theme. PR numbers are in parentheses.

## Security fixes

**Upgrade.** Each defect below let a message from a remote party end the agent runtime, or fail a
queued job again on every tock and every restart. The code each fix replaces is in 2.2.4: the files
named in the PRs exist in the 2.2.4 tag with the unguarded paths. Only #1073 says in its body that
2.2.4 has the defect; for the others the PR bodies describe the behavior before the fix and do not
name released versions. Treat 2.2.4 and earlier as affected, and upgrade. There is no configuration
that avoids them. The relay-only parts (the relaying host's Poster loop, the edge's relay fetch) did
not exist before this train.

### Malformed field values in a well-formed message (#1074)

A message can parse and its SAID can verify while one field value is not valid for its type. Each of
these threw a codec error out of `ProtocolProcessor.dispatch` or out of an escrow pass, which ended
the runtime:

- a receipt or event with a non-hex or over-wide `s`;
- an event with a junk key, next-key digest or witness (`k`, `n`, `b`);
- a `/ksn` reply whose `d` is not a digest;
- `/end/role`, `/loc/scheme` and `/watcher` replies with a non-prefix `cid`, `eid` or `oid`, an
  unparseable URL, or a `dt` that does not encode as a Dater;
- a v2 query with raw signatures, or an exchange with a source seal, whose sender is not a prefix;
- a frame other than a supported `exn` or `xip` that carries a nested message.

One such receipt in a mailbox wedged the poller on every restart, because the cursor is written
only after the consumer returns.

- **Decided once.** Each processor boundary reads the remote field values before any escrow decision
  or store write, through the guarded readers in the new `core/wire-fields.ts`. A reader returns null
  instead of throwing, and treats only cesr's `ParserError` family as malformed input.
- **Typed outcomes.** `Kevery.decideEvent` rejects with `invalidSn`, `invalidPre` or the new
  `malformedField` code. `processReceipt` emits its existing `invalid` cue. Route handlers and
  `Revery`'s `dt` read raise `ValidationError`, which dispatch reports as an `invalidMessage` drop.
  `Exchanger` admission rejects. A nested message on an unsupported frame is an `invalidMessage` drop.
- **Poisoned escrow rows.** Escrow replay goes back through the same checks, so a stored row with a
  malformed value is rejected and removed. An out-of-order rotation with junk keys and an unverified
  `/ksn` escrow no longer fail every pass.
- Dispatch still does not catch codec errors in general.

### The OOBI and authentication loops (#1073)

An authenticated `/oobis` request naming a URL with credentials, an OOBI on a closed port, a host that
answers something that is not CESR, or a response frame whose fields do not decode threw out of the
Oobiery's pass. The queued row was kept, so the throw repeated on every tock and every restart. The
same URLs through an `/introduce` reply or a multi-OOBI reply did the same, as did an unreachable
well-known URL in the Authenticator, and an edge's relay that answered garbage.

- **Failed jobs end as failed.** The queued row is removed, the failure goes to `eoobi.` (or `rmfa.`
  for an authentication) with an `oobiFailed` cue, and the loop takes the next job. The new
  `OobiJobFailure` values are `url-refused`, `egress-refused`, `transport-failed`,
  `unparseable-response` and `invalid-response-frame`. `oobiJobFailure` classifies an error or
  returns null for a fault (a store error, a programmer error), which still propagates.
- **Refused at intake.** `isRequestableHttpUrl` (now also used by `FetchHttpClient.open`) rejects
  what can never succeed: in `OobiRequestHandler.verify`, in `/introduce` (a bad `cid` or URL no
  longer throws `ParserError` or `TypeError`), and in multi-OOBI children, where a bad child URL or
  `aid` fails the parent as `invalid-multi-oobi` before any child is queued.
- **Querier.** A remote `/loc/scheme` location with credentials is treated as no location, so it can
  no longer throw a `ValidationError` out of `deliverDo`.

### Forwarded messages (#1076)

A remote party could end a mailbox-polling agent's runtime, or a relaying host's Poster loop:

- a legacy `/fwd` whose `e.evt` is not a message (`{"t":"zzz"}`) threw from `ForwardHandler.verify`,
  live and on every escrow retry;
- a `/fwd` whose `/e/evt` attachment is not the child's own attachments was accepted and relayed,
  then threw out of `Poster.process`;
- a `/fwd` topic too long to key a mailbox row threw `DatabaseKeyError`, as did a raw `exn` whose
  route made such a topic;
- an accepted location with credentials, or a TCP location with no port, threw out of the Poster's
  pass, and a relay with only such a location read as resolved.

The fix is at the point of origin:

- `ForwardHandler.verify` refuses, as a typed reject, a `/fwd` whose recipient is not a prefix,
  whose topic is empty or not `storableTopic`, or whose child does not parse as exactly one complete
  message with its attachments. Nothing is stored, relayed or ingested for it.
- The Poster decodes each event once. A failure is `UnsendableMessageError`, a failed outcome, and
  the loop continues. A location no messenger can use (`messengerUrl`) is no location.
- `keepRawArrival` keeps only what a processor decided (accept, escrow, KRAM pending or missing, an
  unverified reply) and receipts. A topic the store cannot key is never kept.
- New: `storableTopic`, `messengerUrl`, `UnsendableMessageError`. `messengerFrom` refuses an
  unparseable URL with its `ValidationError` instead of a `TypeError`.

### A peer Grant with a non-canonical registry root (#1070)

A known peer can send a signed v2 Grant whose credential's top-level `rd` is not a SAID, with an
opening attached. The holder escrows it pending. After that, every issuance sweep threw
`UnknownCodeError` from `Manager.hasRegistryRoot`, and `pendingIssuanceGrants` threw too. In 2.2.4
the operation-owner loop caught every error and counted it, so the sweep failed on every pass.
`Manager.hasRegistryRoot` now returns `false` and `getRegistryRoot` returns `null` for a key that is
not canonical; only `putRegistryRoot` still refuses one. The Grant is not resumable, and consenting
to its exchange is refused with a `ValidationError` for that Grant alone.

### The query sender (#1068, #1073)

When the selected attester had no accepted location, `prepareRequest` threw a `ValidationError` that
ended the querier's `deliverDo`, or failed the hosted HTTP request that caused the query. The sender
now chooses at random among the eligible attesters that have a location, never promotes another role,
and leaves the request queued when none has one.

### More remote inputs that ended the runtime (#1079)

A second pass found inputs that parse and still ended the runtime, or wedged an escrow pass on a
stored row. Each is now refused at its point of origin as the processor's existing typed outcome,
before any store write. No broad catch was added.

- **Delegation.** A delegated inception whose delegator's accepted KEL anchors an unknown seal shape,
  or an event seal with junk values, threw from delegation validation and `delegationAncestry`.
  Anchor searches read raw seals through the new guarded reader `readEventSeal` and skip what does not
  decode, as KERIpy does; `Baser`'s sealing-event lookups use it too.
- **TEL.** A `/tsn/registry` or `/tsn/credential` notice whose `dt` is a valid timestamp a Dater
  cannot encode (no fraction, `Z`) is now an unverified notice. A TEL event body was never
  SAID-checked, so an unverified body reached out-of-order escrow and threw on every escrow pass;
  `Tevery.processEvent` now rejects a body that does not verify, a non-hex or unsafe `s`, and an
  `i` or `ri` that is not exactly one qualified prefix, before any escrow.
- **Nested frames and credentials.** A child nested where a flat message is required (a BUP inside
  an Unblind query, an event inside a multisig or IPEX exchange) made `envelopeFromFrame` throw a plain
  `Error`; it raises `ValidationError` and the parent is refused. A credential whose schema
  reference starts with `http://` but does not parse (`TypeError`) names no cached schema, and a
  credential body that is not JSON (`SyntaxError`) fails validation as `invalidSchema`.
- **KRAM.** An exchange message whose stamp a Dater cannot encode, or whose exchange id is not one
  qualified digest (a cache key the pruner could not split), is dropped before any write, with the
  `timestamp` reason or the new `exchangeId` reason.
- **Querier.** A query request that can never be addressed (any unverified reply signed by an
  unknown prefix creates one) rotated in the querier forever. A request with a ready signer and no
  reachable attester is now dropped, with a log, after `UNADDRESSED_QUERY_PASS_LIMIT` passes. A TCP
  query location without a valid port, or on a host without a TCP dialer, is unreachable, not a
  delivery fault.
- **Delegator and witness loops.** A delegator or witness that was unreachable or refused ended the
  delegating loop and the TEL publication loop. The delegation workflow row is kept for the next
  tick (and is no longer removed before its publication succeeds), and a TEL publication stays
  pending for the witnesses that did not take it. New: `deliverWitnessMessage`, `Receiptor.attempt`.

The same PR fixes two stale routing tests: the `/end/role` atomicity test predated the
`endRoleSaved` cue, which is correct (pushed after commit, only for an accepted reply), and the test
now asserts it.

### What this means for real faults

Three catch-alls are gone (#1070; see [Runtime structure](#runtime-structure-changes)). A store
error, corrupt local state or a signer error that gets past `canSign` now ends `runAgentRuntime`
instead of being counted and retried. That is by design: no remote, network or validation outcome
reaches those places.

### Still known and not fixed

From the PR bodies:

- Dispatch does not catch codec errors in general; the cases above are guarded one by one (#1074,
  #1079).
- If a group member is unreachable, every group operation waits on it, including one whose signature
  is not needed. `DeliveryOutbox` is one ordered queue (#1049).
- A relaying agent's failed onward send is logged and not retried or acknowledged to the edge
  (#1058).

## Relay mode

An edge signs locally and hands every message to its agent, which does the forwarding, the way a
KERIA agent re-sends a Signify controller's exchange. Wallet guide:
[Delivering through an agent](../design-docs/runtime/WALLET_LIBRARY_GUIDE.md#delivering-through-an-agent).
A runtime without `relay` or `relaying` behaves as before.

### The edge (#1056, #1060, #1063)

- **`AgentRuntimeOptions.relay`** is a `Relay`: the agent's AID and the agent's own OOBI.
- **Egress guard.** `createAgentRuntime` wraps its HTTP client in `relayOnlyHttpClient`. It refuses,
  as `RelayOnlyError` (a `TransportError`), any HTTP or TCP request whose origin is neither the
  relay's OOBI origin nor one of its accepted locations. It reads the accepted locations on every
  request. If the relay has no accepted location yet, the runtime queues the relay's OOBI.
- **Delivery.** `Poster` sends every recipient other than the relay exactly one `/fwd` to the relay,
  never a direct fallback; the relay itself gets the message directly. While the relay is
  unresolved, delivery fails with `RelayUnresolvedError` and nothing is sent. For a group source the
  local member signs the wrapper.
- **Queries and polling.** With a relay, `WitnessInquisitor` addresses every query to the relay
  (`attestersFor` returns only the relay), and `mailboxPollEndpoints(hab, relay)` returns only the
  relay, never witnesses or other mailboxes.
- **Authorization.** The relay is usable for an identity only once that identity has an accepted
  `mailbox` end role naming it: the `/fwd` wrapper's signer to deliver (for a group, the local
  member), the query's signer to query (the query stays queued until then), the polled subject to
  poll (for a group's mailbox, the group's own row). Without it `Poster` fails the delivery with
  `RelayUnauthorizedError` and sends nothing. `relayRefusal` is the one decision, `relayAuthorized`
  reads the row. A message addressed to the relay itself needs none, so onboarding is unchanged.
- **OOBIs and schemas.** The Oobiery never fetches a third party's URL. It sends the existing
  `/oobis` exchange to the relay, signed by a local identifier that authorized the relay as its
  mailbox, and reads the result from the relay's OOBI endpoint, verifying as for a direct fetch. A
  controller, witness, agent or mailbox OOBI `.../oobi/{cid}/{role}[/{eid}]` maps to the same path
  on the relay; a schema OOBI `.../oobi/{said}` maps to `oobi/{said}`. The relay's own OOBI and
  any URL on an accepted relay location are fetched directly (`isRelayOrigin`).
- **Waiting.** While the relay answers 404, is unreachable or answers without the controller's KEL,
  the job stays queued as `relay-requested` (or `relay-pending` before the relay can be asked), and
  waiting jobs take turns. After `RELAY_OOBI_TIMEOUT_MS` (30 seconds from the first attempt, on the
  runtime clock) it fails as `relay-unresolved` or `relay-unserved`. A URL naming neither an
  identifier nor a SAID fails at once as `relay-unmappable-oobi`.

### The agent (#1058, #1063, #1068, #1069, #1075)

- **Enabling.** `AgentRuntimeOptions.relaying`, or `HostKernelSpec.enableRelay` in
  `@keri-ts/hosting` (now required). Relaying needs a mailbox store.
- **`/fwd` hand-off and re-forwarding.** `ForwardHandler` takes exactly one path per `/fwd`:
  1. the recipient is a habitat of the agent's own Habery and the sender is served: the child goes
     through the agent's own Reactor as remote input to that habitat's endpoint, so signature, KRAM
     and escrow rules apply;
  2. this host is the recipient's witness, mailbox or agent: the child is stored;
  3. the sender is served and the recipient is remote: the child goes out through the agent's Poster
     to the recipient and topic the `/fwd` names;
  4. otherwise the `/fwd` is dropped.

  A served sender authorized this host as `mailbox` or `agent`. A group's `/fwd` is signed by its
  local member, so the agent also reads the group's own row, but only for an accepted member of that
  group. Witness membership alone never grants relaying. There is no new route or wire format.
- **`/oobis`.** A relaying agent accepts the request only from a served sender, by the same rule. In
  `@keri-ts/hosting` its OOBI endpoint also answers for any identifier whose accepted KEL it holds,
  through its service habitat, as KERIpy's `OOBIEnd` does.
- **On-demand refresh.** When a relaying agent processes a `logs` or `ksn` query from a served,
  authenticated sender about a subject that is not its own, and it can address an attester for the
  subject, it also queues its own `logs` query for the subject (`relayRefreshCue`). It still answers
  the edge from what it holds; a query naming a sequence number or anchor the agent lacks is escrowed
  and answered after the refresh lands. `tels` queries are not refreshed. Nothing is watched or
  stored. `WitnessInquisitor.enqueueCueOnce` drops a request identical to one queued, in every
  relaying runtime.
- **Hosted ingress.** `drainRuntimeCues` only routes cues. Queries a request causes are sent by the
  query-sender worker on its tock, so such queries leave up to one protocol tock (31.25 ms) later,
  after the request is answered. This applies to every hosted runtime.
- **Mail for pickup.** A host that is the `mailbox` or `agent` of a local group (the edge's group,
  whose co-member it hosts) ingests a third party's `/fwd` for the group once and stores one copy for
  the remote member. An edge's own `/fwd` is ingested and not stored (`ownTraffic`). The rules are in
  `app/mailbox/agent-inbox.ts` (`authorizedStoringHost`, `keepsForPickup`, `ownTraffic`).
- **Raw mail.** For an identifier that authorized the host as `agent`, a raw inbound post (KERIpy's
  `sendDirect`) is kept once by `keepRawArrival` (exported from `keri-ts/runtime`). It is not kept
  for the `mailbox` role, whose senders use `/fwd`. Poster delivers to a recipient whose agent is a
  local identifier through the local mailbox store.
- **Processed once.** A host that is the `mailbox` or `agent` of a local group processes mail for it
  exactly once: arrival is the only local delivery, on a relaying and a non-relaying host, and
  `MailboxPoller.deliveredOnArrival` stops the host polling its own mailbox for that group. A local
  single-signature habitat is unchanged (loopback poll). This also fixes, on non-relaying hosts, a
  group that named the host only as `agent` never processing its `/fwd` mail, and an edge getting its
  own `/fwd` to its group back (#1075).

### What a relay can and cannot do

From the wallet guide. The agent can drop, delay, reorder and observe everything the edge sends and
receives, including plaintext CESR mail. It cannot forge or alter a signed message: the edge signs
locally and every recipient verifies against the signer's KEL. The edge's view of third-party key
state is the agent's: it can verify that what it receives is valid, not that it is current, and an
agent can withhold a rotation. `sent` from Poster means the agent accepted the wrapper, not that the
recipient received it.

Refused behind a relay for now, failing closed as `RelayOnlyError` rather than going direct:
delegation, TEL receipting, witness TOTP registration and well-known authentication. Use `"direct"`
for a wallet that needs them.

### Onboarding order

The agent is useful only once these are done, in this order. `wallet.relayStatus()` lists what is
missing:

1. resolve the agent's OOBI (`resolve-oobi`);
2. authorize the agent for each single-signature identifier (`authorize-member`):
   `mailboxes.add(pre, relay.aid)`;
3. incept the group, if any (`groups.incept`);
4. authorize the agent for the group (`authorize-group`): `groups.proposeMailbox`, the co-members
   approve, `groups.completeMailbox`.

### The wallet and tufa (#1071)

- **`OpenWebWalletOptions.delivery: WebWalletDelivery`** is required: a `Relay` (`{ aid, oobi }`),
  passed to `createAgentRuntime` as `relay`, or `"direct"`, which composes the runtime as before.
  Omitting it does not compile. A relay with an empty AID or a non-HTTP(S) OOBI rejects with
  `ValidationError` before any store opens (`assertRelay`, which the egress guard also calls).
  `recoverWebWallet` reopens with the same `delivery`.
- **`relayOnboarding(hby, relay)`** (keri-ts) lists the steps still missing. `WebWallet.relayStatus()`
  returns it.
- **`health()`** gains `relay-unresolved` and `relay-unauthorized` (with the identifiers). They sit
  after `latched` and before `mailbox-unreachable` and `signer-unavailable`. There is no
  `relay-unreachable`: an agent that stops answering polls is retried with backoff and not reported.
- **tufa.** `tufa agent --relay` and `tufa mailbox start --relay` turn relay mode on for the host
  (off by default). The witness host stays off. The tufa witness and indirect hosts pass
  `enableRelay: false`.

## Groups

### Member replacement retires the old member (#1043, #1045)

`replaceGroupMember` left the replaced member behind as a local identifier with stored keys. It now
retires it.

- **`Habery.retireHab(pre): RetiredHab`** retires one local, non-group habitat at the store level. In
  one transaction it deletes the `habs.` record and the `names.` mapping and the Keeper's stored key
  rows (`Manager.forget`: `prms.`, `sits.`, `pubs.`, and the `pris.` seeds). It makes no event and
  signs nothing. `RetiredHab` is `{ pre, name, domain, keys, released }`.
- **Kept on purpose:** the KEL and its attachments, `states.`, receipts, every accepted reply the
  identifier authored or that names it, KRAM rows and the Kever cache entry. KERI never deletes a
  KEL, and BADA/RUN orders new replies against the stored ones, so deleting them would let an older
  signed reply be accepted again. After retirement the identifier is an ordinary remote one, also
  after a reopen.
- **Refused** (`ValidationError`, before any write): a prefix that is not a local habitat, a group
  habitat, a local group's recorded or accepted member, the delegator of a local habitat.
  `Habery.retireRefusal(pre)` returns the reason without throwing.
- **Derivability.** Retirement deletes the stored keys, not the secret's derivability: a rooted
  salty habitat's seeds stay derivable from the Keeper's root salt plus namespace and name.
  `Manager.incept` refuses any inception whose first key belongs to a forgotten prefix, in either
  transferability encoding. A retired name cannot be reused with the same salt and namespace.
- **`Hab.make`** no longer leaves `habs.`, `names.` or Keeper rows behind when local acceptance of
  its inception fails.
- **`retireIdentifier(runtime, pre): RetiredIdentifier`** (`keri-ts/runtime`) retires a local,
  non-group identifier from a running agent: it calls `retireHab`, releases the held signers of the
  current keys, deletes the identifier's mailbox poll cursors (`tops.`) and KEL publisher rows
  (`kpub.`), and prompts the poller and publisher. It returns `{ pre, name, released, mailboxes }`.
  `retireIdentifierRefusal(runtime, pre)` reads the reason. It also refuses a registry issuer, a
  pending delegated event of `pre` or `pre` pinned as a delegation proxy, the habitat of a live
  issuance or Unblind, the source of a queued Poster event, the signer of a queued query and the
  querier's configured signer. A poll that ends after its subject was retired no longer writes its
  cursor back.
- **`replaceGroupMember`** retires the replaced member by default. If a refusal applies, the
  replacement still succeeds and the member is kept. `ReplacedGroupMember.previousMember` is
  `{ kind: "retired", retired }` or `{ kind: "kept", reason }`. `keepPrevious: true` keeps it.
- **Wallet.** `identifiers.retire(pre)` retires a single-signature identifier. `groups.replaceMember`
  passes `keepPrevious` (options are the named `ReplaceMemberOptions`) and returns the outcome. After
  a replacement that retires the old member, `health()` reads `ok`.
- **Poller follows (#1039).** After `replaceGroupMember`, the mailbox poll worker polls as the new
  member without reopening: the signer prefix is part of the worker key, a halted worker clears the
  signer condition it reported, and `replaceGroupMember` prompts the poller, the KEL publisher (an
  expired budget re-arms) and the root replicator.

### Stored member lists follow accepted state (#1053, #1062)

A local group's stored members (`smids`, `rmids`) followed a rotation only when the caller ran
`settleProposedRotation` or the store reopened. A proposer whose own signature cannot complete a
rotation (a weight-0 member) saw it complete later, and its group messages, IPEX traffic and root
copies kept going to the old member.

- **`Habery.alignGroupMembers(pre)`** is the one writer of a group's member lists after its record is
  created. Members come from accepted key state only (`acceptedGroupMembers`), never from a
  proposal's or a caller's lists. It returns `aligned`, `unchanged` or `unattributed`; when a key
  cannot be attributed yet (a member's KEL is missing) it writes nothing.
- **The Counselor runs it** at the start of each pass for every local group whose latest
  establishment SAID differs from the one last found aligned. Reopen recovery, KEL approval,
  `joinGroupHab` replacement and `rotateGroupHab`'s immediate acceptance call the same function.
- **Decks (#1062).** The Counselor takes `rotated?: Deck<RotatedCue>` and `groupChanges?: Deck<string>`
  and pushes a group's prefix on `groupChanges` when an establishment event completes or members are
  aligned late. The root replicator treats each as a prompt, so a member rotated in no longer waits
  for the 60 s sweep. The sweep now also keys each group on its stored signing members.
- **The recorded local member (`mid`) is never changed** by alignment; `replaceGroupMember` stays the
  explicit call. Unlike KERIpy's `recoverAcceptedMembers`, the lists follow accepted state even when
  it does not include the local member, so a member whose join is not yet accepted, and that holds
  the group's KEL, records the group's current accepted members until the join rotation is accepted.
- **Weight plays no part** in membership or delivery.
- **Removed:** `settleProposedRotation`, `ProposedRotation`, `commitAcceptedGroupMembers`, the public
  `commitGroupHabMembers`. `recoverAcceptedGroupMembers` is now `alignGroupMembers`. The wallet's
  `groups.rotate` no longer settles.

### Weight-0 members (#1049, #1051, #1066)

A signing member with weight 0 is still a member.

- **Delivery ignores weight.** The issuer delivers the Grant to the weight-0 member's endpoint, and
  the edge member sends it the DH reply, DH proof and Admit wrappers; the replicator sends it the
  registry root.
- **`followGroupIssuanceProof`** worked only for an issuer group, so a weight-0 holder could never
  accept a Grant the group completed without it. It now takes the issuer role when the Grant's sender
  is a local group and the holder role otherwise. It still signs nothing (#1049).
- **Automatic follow (#1066).** The issuance owner's sweep (`ISSUANCE_SWEEP_MS`) now begins the
  proof-only follow of a pending group Grant, as issuer or holder, when the member has no live, ended
  or complete operation for it, the Grant is inside its deadline, and the custodian's
  `/multisig/ipex-proof` wrapper for that Grant is stored. The proof is the trigger because it exists
  only after the key exchange finished, so a member whose signature is still wanted is never followed
  in its place. A follow signs nothing, so it is not held back while the member cannot sign, and a
  restart begins it again from the stored proof. `followGroupIssuanceProof` is idempotent and stays
  for a proof supplied as bytes.
- **Status.** Before the proof or a root copy is stored, the member reads `awaitingExchangeConsent`.
  With either it reads `active` / `awaitingAnchor` instead of `interrupted`.
- **Still explicit:** approving the group's Admit (`approveGroupIpex`), which matches KERIpy.
- **Non-transferable edge member (#1051).** A test covers the shape the product deploys: a
  weight-1 non-transferable edge member and a weight-0 custodian that holds the only next-key
  commitment, through issuance, a rotation to a second edge member and a retained credential. No
  library change was needed.

### A host delivers a co-hosted group's mail once (#1069, #1075)

See "Mail for pickup" and "Processed once" under [Relay mode](#relay-mode).

### Group IPEX prerequisite as data (#1064)

A group presentation Grant that waits for its presentation registry update no longer stores a
closure. `GroupIpexPrerequisite` is `{ anchor, grant, opening }`. On each tock `GroupIpexOperations`
reads the stores; once the update is accepted it attaches the proof and signs this member's
contribution. A Grant whose own KRAM window passed while it waited still ends `expired`. A superseded
update (another accepted KEL event at the anchor's sequence number, or another accepted TEL event at
the update's) now ends the operation `failed` naming the superseding event, where it used to wait
forever. An update the members never approve still waits until `abandonGroupIpex`.

## Recovery and refill

### Persistence queue (#1046)

`PersistenceQueue` latched on its first failed task, so one transient IndexedDB abort ended every
later commit of a browser composition.

- **Retry before latching.** A failed task is retried in place on `PERSISTENCE_RETRY_DELAYS` (25, 100
  and 400 ms, four attempts) and keeps the head of the queue, so prefix durability holds. It latches
  only when every attempt fails. A write on a connection lost to another tab's `versionchange` never
  reconnects, so it fails every retry and still latches.
- **`read(task)`** runs in queue order and returns the task's result. A throwing read rejects only
  its caller with `PersistenceReadError`, is never retried and never latches. After a latch it still
  runs and sees the durable prefix.
- **`status()`** returns `PersistenceStatus`: `"healthy" | "retrying" | "latched"`.
- **`PersistenceLatchedError`** (cause: the first failure) replaces the generic
  `DatabaseOperationError` from `assertHealthy`, `flushed`, `joined` and `close`.
- **Web wallet:** `persistenceStatus()` and `readPersisted(task)`.
- A latch is terminal for the composition; recovery is reopening (ADR-0015 rule 3).

### Rejoin, recover, salt (#1048, #1050, #1055)

- **`rejoinGroup(deps, { oobi, group, member, alias, timeoutMs, domain? })`** (`keri-ts/runtime`)
  rebuilds a group record from the group's accepted key state after a lost store. It queues the OOBI,
  waits (bounded by `timeoutMs` on the runtime clock) for the OOBI and the group's key state, reads
  the signing and rotation members with `acceptedGroupMembers`, records the group with
  `joinGroupHab` and prompts the poller, publisher and replicator. Outcomes are values: `joined`
  (with `written`), `not-member`, `oobi-failed`, and `timed-out` with
  `waiting: "oobi" | "group-key-state" | "member-key-state"`. Only `joined` writes. A group OOBI
  carries only the group's KEL, so the caller must resolve the co-members' OOBIs first, or the
  result is `timed-out` waiting on `member-key-state`. Wallet: `groups.rejoin(options)`.
  `written` (#1065) is true when the call wrote the record, false when it was already there; a
  written record is the signal to refill.
- **`recoverWebWallet(wallet, { open, group?, attempts? })`** (`@keri-ts/wallet/web`) closes the
  handle, reopens with `open` (up to `attempts`, default 3, 250 ms apart), and returns
  `{ wallet, rejoin }` or `{ wallet, rejoin: null, skipped }` with
  `skipped: "no-group" | "group-recorded" | "member-missing"`. A reopen that fails every attempt
  throws `WalletRecoveryError`. With `group` (`RecoverGroupOptions`) it resolves `memberOobis` and
  calls `groups.rejoin`. On `member-missing` it does not create the member; the host re-adopts it
  (`hby.makeSignedHab` from the signed inception, hold its signer, resolve the co-members' OOBIs,
  `groups.rejoin`). `readPersisted` on a closed or stopped wallet now rejects with
  `WalletStoppedError`.
- **Keeper salt.** `openWebWallet` takes an optional `salt` (qb64 of a 128-bit root salt), so a fresh
  store opened with the same passcode and salt derives the same signator and salty identifiers. A
  malformed salt rejects with `ValidationError` before any store opens; a salt that differs from the
  one the store holds rejects with `KeeperSaltMismatchError` after the wallet closes what it opened.
  The guide lists what the passcode and salt re-derive and what they do not (held signers, random
  keys, registry roots, the group record, the inventory).

### Refilling credentials from a co-member (#1057, #1059, #1065)

- **`listGroupDisclosures(hby, exc, group)`** returns each accepted v2 Grant that an accepted Admit
  answered, as `holder` or `issuer`. "Accepted" means the Exchanger's own `exns.` record, which is
  written only once the sender's threshold is met.
- **`exportDisclosureStream(discloser, hab, grant)`** returns one stream in dependency order: KELs
  with their delegation ancestry, the accepted TEL of every registry the carried nodes name, the Grant
  with its nests, the Admit. It signs nothing, so the exporting habitat needs no usable key (a
  weight-0 custodian can serve it). Schemas, registry roots, the group record, OOBI replies and
  `/multisig/*` wrappers are not in it. `RegistryStore.registries(issuer?)` lists accepted
  registries.
- **Retained import.** `importCredentialStream` now accepts v2 `rip`/`bup` (at their exact ordinal in
  the v2 registry store) and v2 Grants and Admits (accepted by the Exchanger; an Admit also needs its
  Grant's reply row to name it), and reports the rest in `unaccepted`. Its frames carry
  `DispatchOptions.retained`, which skips `kramer.intake` for a v2 `exn`/`xip`, so a stale exchange
  is accepted. Signatures, sender policy, route verification and escrows are unchanged, and queries
  and replies still pass KRAM. Network inputs cannot set it: `IngressOptions` extends the new
  `IntakeOptions` (`local`, `mailboxAid`, `escrows`), and only `importCredentialStream` sets
  `retained`. A retained exchange raises no notice and has no lifetime.
- **Wallet.** `credentials.importStream(bytes, options?)` runs the import against the wallet's
  runtime (`ImportStreamOptions.timeoutMs`). `credentials.rebuild()` writes the inventory rows the
  imported history proves: an `admitted.` row for every accepted Grant addressed to a local
  identifier whose accepted Admit answers it (`Wallet.reconcileAdmissions()`, checked against the
  history the pair was accepted under, so a credential revoked since is still listed as held), and an
  `issued.` row for every accepted Grant a local identifier sent of a credential it issued, once the
  wallet holds the registry root. Explicit and idempotent. `Wallet.recordAdmission` is unchanged and
  still requires current standing.
- **Trust.** Each artifact is verified: KELs, TEL, Grant and Admit are checked by the importing
  store. Nothing proves the set complete or current. An interrupted refill is repaired by comparing
  both sides' `listGroupDisclosures`. Credentials, registry state and exchanges are not restored by
  `rejoin` or `recoverWebWallet`. The guide's "Refilling an empty store from a co-member" gives the
  sequence.
- **Wallet issuance tracking (#1067).** The wallet tracks an issuance in flight as plain data
  (`TrackedIssuance`) instead of a stored function. `recordFinished` records it. The unused
  `IssuanceRecorder` type is no longer exported from `web.ts`.

## KRAM made explicit

Before, `Kramer.intake` returned `{ kind: "drop", reason }` that most callers discarded.

- **Refusal record and log (#1037).** `Kramer` takes a `Logger` (default `consoleLogger`) and logs each
  refused message once: SAID, sender, ilk, route, reason, stamp, deadline. Timestamp, timeliness,
  unknownThread, lifetime and authentication refusals log at warn; replay logs at debug. Timeliness
  and lifetime refusals carry the `deadline`, the last receiver instant the message was acceptable
  (stamp + drift + lag, as KERIpy's `Kramer.deadline`; or opener + exchange window). The reason union
  is the named `KramRefusalReason`. `Kramer.prune` warns once per incomplete multi-signature message
  it expires, and `KramPruneResult` gains `partials`.
- **`KramRefusedError`** (a `ValidationError` with `said` and `refusal`), with `KramTimeRefusal`,
  `KramStageRefusal` and `KramRefusalReason`, is exported from the runtime.
- **Group IPEX `expired` (#1041).** A group member's own contribution refused by its own KRAM used to
  retry every 250 ms until `waitForGroupIpex` timed out. `proposeGroupIpex` and `approveGroupIpex` now
  throw `KramRefusedError` (for `timestamp`, `timeliness`, `unknownThread` or `lifetime`; `replay` is
  not an error). `GroupIpexOperations` ends the operation `expired` with the KRAM reason and deadline,
  and `"expired"` is added to `GroupIpexEndState` (the wallet's `EndedGroupIpex` follows).
- **Issuance expiry (#1042).** Past its deadline an exchange's cache row is pruned and an expired
  pending Grant is ejected with its only stored body, which made `issuanceStatus` and friends say "No
  issuance was begun". `Exchanger.exchangeExpiry(said)` now answers after the prune and the ejection.
  An in-memory map of ejected Grants' lifetimes is lost on restart, and after a restart an ejected
  Grant reads as unknown again. Past the deadline `issuanceStatus`, `approveIssuanceExchange`,
  `beginIssuance` and `selectGrant` (so `receiveIssuance`) throw `KramRefusedError` (reason
  `lifetime`, with the deadline), and the `expired` status carries `deadline`.
- **`pendingApplies`.** An expired Apply stays out of the list after KRAM prunes it; it used to
  reappear as pending with `deadline: null`.
- **Hosting ingress 422 (#1040).** Generic CESR ingress answers 422 with `KRAM refused message: <reason>` when the final non-query frame is dropped for `timeliness`, `lifetime` or
  `unknownThread`. These are decided only after a signature or anchored seal verified, and accepted
  and replayed messages still answer 204, so the status is no replay oracle for an unauthenticated
  prober. `replay`, `authentication`, `missing`, `pending` and `timestamp` still answer 204. No
  deadline or clock detail is disclosed. KERIpy always answers 204; this diverges deliberately.
- **`kramRefused` change (#1047).** For those three reasons `Kramer.intake` publishes a `kramRefused`
  cue (`KramRefusedCue`), which `processCuesOnce` pushes to the new `AgentRuntime.changes` sink as a
  `KramRefusedChange`. The Signaler writes it under `/workflow/kramRefused`, collapsed per SAID. The
  cue is transient, with no durable record. `ChangeSink.push` takes a `RuntimeChange`
  (`WorkflowChange | KramRefusedChange`). `isKramLateReason`, `KramLateReason` and `kramExchangeId`
  sit beside `KramRefusalReason`.

## Runtime structure changes

### Signer availability is state (#1052)

Replaces the released-signer machinery from #995 with a state read.

- `Manager.hasSigner(pub)`: held, or stored in `pris.`, without decrypting.
- `Hab.canSign()`: a pure lookup over the keys `Hab.sign` would use; a group answers through its
  local member. It no longer makes a probe signature.
- `Habery.unsignable(): UnsignableHab[]`: accepted local habitats with the keys they lack, derived
  on every read.
- Every background pass that signs reads `canSign()` and skips through the path it already had: the
  mailbox poller (no poll, no backoff, polls within one tock of `Manager.hold`), the querier (to the
  tail), cues (`Respondant.enqueueCue` returns `CueOutcome`: `taken`, `unrouted`, `unsignable`; an
  unsignable receipt, witness or reply cue is re-appended), delegation (keeps its row), Poster
  (reports the forward as failed, still no retry), Counselor and root replicator (keep the copy
  without spending an attempt), `RegistryRoot` (copy stays pending instead of dropped as refused), and
  the issuance, group IPEX and Unblind owners (skip the operation after the deadline check).
- Opening a store without a signer stays legal; the habitat is listed by `unsignable()` and acts on
  the next tock after `Manager.hold`.
- A `SignerNotHeldError` that still escapes a loop is a fault and ends `runAgentRuntime`.
- `Manager.forget(pre, current)` also drops the held signers of `current` and returns
  `ForgottenKeys` (`deleted`, `released`). Hosts need no `release()` call after close or after
  `groups.replaceMember`.
- Wallet `health()`: `{ status: "signer-unavailable"; identifiers: readonly UnsignableHab[] }`,
  derived on read, below `mailbox-unreachable`.

### Callbacks become cues and decks (#1054, #1062, #1064, #1067)

- `Revery.onEndRole` becomes an `endRoleSaved` cue (`EndRoleSavedCue`) after an accepted `/end/role`
  reply commits. `processCuesOnce` and the witness cue drain hand a mailbox role to the KEL publisher
  and the mailbox poller.
- The poller's `onPolled` and `onUnauthorized` become `MailboxPollCue` records (`polled`,
  `unauthorized`) on the KEL publisher's new `polls` deck. The 403 repair, with its `kpub` write, now
  runs on the publisher's fiber, and `KelPublisher.repair` is private.
- `QueryReply.observeReady` is replaced by a state read: the TCP witness host re-reads
  `QueryReply.ready` on a one-tock timer.
- The Counselor's `GroupMailboxes` callback becomes the `rotated` and `groupChanges` decks (above),
  and `GroupReceipting.receipt` options gain `allowTcp`, so composition passes the `Receiptor`
  directly.
- Group IPEX prerequisites and wallet issuance tracking are plain data, not stored functions (above).

### Catch-alls removed (#1070)

Three places caught every error and kept going, so a damaged store or missing durable state was
counted and retried instead of stopping the agent: the operation-owner loop (`operations.health`),
the KEL publisher loop (`publisher.health`), and `Counselor.forwardCompleted` (turned into a `failed`
forward and retried up to eight times). They now catch nothing. Below them, a failed post, delivery
or member forward is already a typed `failed` result. What remains is store errors and corrupt local
state, which end `runAgentRuntime`. Halting the runtime is not a fault and stays clean.

- **`MissingDurableStateError`** (a `DatabaseError`) is thrown by `localGroupMember` when a group's
  record names a member the store's habitats do not include. Retirement refuses a group's member, so
  no remote message can cause it. Because it is not a `ValidationError`, callers that turned a
  `ValidationError` into a drop or refusal now let it propagate: the ingress `isInvalidMessageError`
  drop, `Dhke` and `Unblind` `processQuery`/`processReply`, `Unblind.restoreHeld`/`retryWaiting`,
  and `pendingIssuanceGrants`/`pendingGroupGrants`. A prefix that is not a local group still throws
  `ValidationError`.
- `UnblindingOperations.active()` no longer reprocesses held queries for a habitat that cannot sign.
- Wallet `health()` no longer has `faulted`: a loop fault ends the runtime, and `health()` reads
  `stopped` with the fault as `cause`.

  `polls`); `QueryReply.observeReady` (read `QueryReply.ready`) (#1054).

  health status (#1070).
- `HaberyArgs.tier` (#1055).

**Renamed or changed shape**

- `Habery.recoverAcceptedGroupMembers` is now `alignGroupMembers` (#1053).
- `Manager.forget(pre, current)` returns `ForgottenKeys`; `RetiredHab` gains `released` (#1052).
- `Respondant.enqueueCue` returns `CueOutcome`, not a boolean (#1052).

  its cues (#1063); `ProtocolProcessor` takes a trailing `relaying` flag (#1068).

**Behavior and error changes**

- `replaceGroupMember` retires the replaced member by default (`keepPrevious: true` keeps it) (#1045).
- A retired name cannot be reused with the same salt and namespace; `Manager.incept` refuses a
  forgotten prefix (#1043).
- `localGroupMember` throws `MissingDurableStateError` for a missing member; a real fault in a

- `issuanceStatus`, `approveIssuanceExchange`, `beginIssuance`, `selectGrant` throw
  `KramRefusedError` past the deadline; `proposeGroupIpex` and `approveGroupIpex` throw it for a
  refused own contribution (#1041, #1042).
- Generic CESR ingress answers 422 for a late non-query message (#1040).
- `Manager.hasRegistryRoot` and `getRegistryRoot` answer `false` and `null` for a non-canonical key

- `envelopeFromFrame` throws `ValidationError`, not a plain `Error`, for a nested child where a flat

- `Tevery.processEvent` rejects a TEL body that does not verify, before any escrow (#1079).
- `FetchHttpClient.open` and `messengerFrom` throw `ValidationError` for an unparseable URL, not
  `TypeError` (#1073, #1076).
- `drainRuntimeCues` no longer runs a query-sender pass inside the request (#1068).
- `readPersisted` rejects with `WalletStoppedError` on a closed or stopped wallet (#1050).
- `openWebWallet` rejects a mismatched root salt with `KeeperSaltMismatchError` (#1055).

## Not tested

Each PR ran its own files locally in Docker, once; CI jobs were skipped by the owner's instruction
for the implementation PRs. The following are named in the PR bodies as not exercised or not decided:

- **Unsignable skip paths (#1052):** the Counselor forward, the root replicator, `RegistryRoot`
  pending, the issuance, group IPEX and Unblind per-operation skips, Unblind `adopt()`, and delegation
  advancing later rows while one is kept. No test runs them with an unsignable habitat.
- **KERIpy `main` (#1077, #1080):** the relay interop, single-signature and group, was proven against
  the pinned candidate only. The checks against upstream `main` are ignored expected failures:
  `main`'s `StreamPoster` fails with a transferable mailbox identifier, `main` opens IPEX v2 with an
  `exn` where keri-ts requires an `xip`, `main` drops every `xip`, and `main`'s Parser has no v2 TEL
  route. Testing against `main` is a follow-up.
- **Group issuance and a full group conversation with KERIpy (#1080):** a group-issued credential is
  not tested, since group issuance by keri-ts to KERIpy is not. In "relay group to KERIpy", the
  agent logs a KRAM `unknownThread` refusal for KERIpy's Admit of the group's presentation Grant: the
  co-hosted weight-0 custodian holds only the proposal of that Grant. The edge still receives the
  Admit through the group's mailbox. Not fixed.
- **Verifier DH and Unblind through a relay (#1072):** in the tested shape the verifier needs no DH
  or Unblind query, so that path is not exercised through the agent.
- **Relay delegation (#1068):** the plan lists delegation as not yet rerouted, and the edge enqueues
  the delegator's anchor query only when it holds the delegator's witness location.
- **One-shot queries (#1068):** the finite workflows in `querying.ts` have no retry timer; a one-shot
  `ksn` or ungated `logs` query gets the agent's current state and only a later query sees the
  refresh.
- **Retained Grants that re-present a credential (#1059, #1065):** a Grant in which a Grantor
  re-presents a credential naming a presentation registry has no receiver receipt, so the IPEX handler
  refuses it on import. A direct issuance Grant, the case tested, needs none.

## Known limits

- The relay refusals under [What a relay can and cannot do](#what-a-relay-can-and-cannot-do):
  delegation, TEL receipting, witness TOTP registration and well-known authentication fail closed.
- A relaying agent has no outbox and no acknowledgement back to the edge for a failed onward send.
- The `kramRefused` cue is transient; nothing durable backs it.
- After a restart, an ejected expired Grant reads as unknown again (#1042).
- Retirement markers do not outlive the store: a fresh store re-derives a retired salty identifier
  from its salt (#1043, #1055).
- The items under [Still known and not fixed](#still-known-and-not-fixed).
