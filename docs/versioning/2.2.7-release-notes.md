# 2.2.7 release notes

Published versions: `keri-ts`, `@keri-ts/hosting`, `@keri-ts/wallet` and `tufa` 2.2.7;
`@keri-ts/registrar`, `@keri-ts/verifier` and `@keri-ts/observer` 2.2.5. `cesr-ts` stays at 2.2.1.

2.2.7 changes how keri-ts gets its LMDB binding and removes storage work that did not need doing.
Nothing here changes a wire format, an event or the signature of a call. One change affects stored
data: read "Before you upgrade" first. PR numbers are in parentheses. Package changelogs list every
change.

## Before you upgrade

keri-ts now writes LMDB data format version 1, the format KERIpy reads, on every install. Earlier
published versions depended on stock `lmdb`, which writes data format version 2 unless the consumer
rebuilt it.

- **You never rebuilt the LMDB addon.** Your stores are in format version 2. This release cannot open
  them, and LMDB crashes the process on the attempt instead of raising an error. Start from fresh
  stores.
- **You already built the data-v1 addon yourself.** Your stores are in format version 1 and open as
  before. Delete your own build step: the prebuilt binary replaces it.
- **Browser wallets on IndexedDB** are not affected.

## Changed

### LMDB comes prebuilt from `@keri-ts/lmdb-js` (#1105)

keri-ts depends on `@keri-ts/lmdb-js` 3.5.10-v1.2 in place of `lmdb` 3.5.3. It is lmdb-js 3.5.10
compiled for LMDB 0.9.29 (data format version 1), N-API only, with the environment close fix below.

- It ships prebuilt binaries for Linux x64 and arm64, on glibc and on musl (Alpine), and for macOS
  arm64. The installer picks the one for the machine. Nothing compiles and no install script runs.
- On any other platform the package compiles from source at install, which needs install scripts
  enabled and a C++ toolchain. That path is not tested by keri-ts.
- Deno on Alpine is not supported: Deno publishes no musl build.
- The in-place rebuild is removed: `setup_lmdb_v1.sh`, the `setup` and `setup:compat-lmdb` tasks and
  the `LMDB_DATA_V1` switch.

`@keri-ts/lmdb-js` is a fork that exists while the close fix is in review upstream
(kriszyp/lmdb-js#388). It will be retired when upstream ships the fix in a data-v1 release.

## Fixed

### Closing a store did not close it (#1103, #1105)

In a data-v1 build, lmdb-js never called LMDB's own close. Each closed store kept three file
descriptors and two memory maps, one of them the store's full map size. An agent has six stores, so
each agent close leaked 18 descriptors and 60 GiB of address space at the default map size. A
process that opens and closes agents ran out of descriptors.

The fix is in the binding: an opened environment is now registered so the existing close path runs.
Sixty open and close cycles of a full agent went from 1,103 open descriptors and 3,621 GiB of
virtual size to 23 descriptors and a flat 19.9 GiB.

One behaviour is new. If one process opens the same store path twice at once, closing one handle now
releases the process's lock on the store while the other is still open. LMDB documents that pattern
as unsupported.

### Creating a store made one synced commit per table (#1101)

Each store now creates all of its named tables in one write transaction. Creating a fresh agent goes
from 191 synced commits to 24, and reopening one goes from 173 empty commits to 6. A crash during
first creation leaves a store with all of its tables or none, and the next open completes it. Key
creation and every other data write keep their own synced commits.

This also applies to the wallet's and the verifier's own stores.

### Idle agents opened write transactions (#1100, #1104)

Loops that only check for work now read first and open a write transaction only when there is
something to write.

- An idle agent opens no write transaction. Before, it opened one or two a second, more with cached
  replay-protection rows, pending exchanges or events waiting in escrow.
- Putting a row that already exists, or deleting one that is absent, is answered from a read.
- A pending exchange that is still waiting on the same dependency is retried without a write
  transaction. Before, one pending Grant made the escrow loop run again on every tick.

What is accepted, escrowed or rejected is unchanged, and so are the cues.

## Interop

KERIpy and keri-ts answer each other's missing-anchor `logs` query in both directions (#1099). The
test withholds the anchoring event from the holder, so the event can only arrive as the answer to
the query. The KERIpy candidate is still `kentbull/keripy` `v2-spec` at `06aa382e`.

## Not tested

- The missing-anchor query through a mailbox or relay, its upper bound, and witnessed issuers.
- keri-ts on the prebuilt binary for Linux x64 on musl, beyond the binding package's own install and
  load check.
- The source-compile fallback of `@keri-ts/lmdb-js` on platforms without a prebuilt binary.
- End-to-end issuance time on this release.

## Known limits

- A consumer that builds its own data-v1 addon does not get the close fix from this release. It has
  to move to `@keri-ts/lmdb-js` or apply the fix to its own build.
- Each Grant still carries the issuer's whole log on its first send, so issuance time grows by about
  0.1 s per issuer event. Sending a contact only what it lacks is planned work.
- A message sent through the delivery queue still waits one 31 ms tick per send, and a relay still
  runs an escrow pass for every inbound frame. Fixes for both are planned.
- A live duplicate or rejected event, and a message dropped by replay protection, still open one
  empty write transaction each.

## Upgrade

There are no API or wire changes. Check "Before you upgrade" for the storage format, then upgrade in
place.
